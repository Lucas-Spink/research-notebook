# ADR-0040: Rich section editors and passthrough blocks

- Status: Proposed
- Date: 2026-09-24
- Deciders: maintainer
- Spec sections affected: 7.7 (FR-EDT-01 to FR-EDT-03); gate S4-G08

## Context

S2-T12 (ADR-0028) built Methods, Results Notes and Interpretation as plain `<textarea>` fields, deliberately deferring rich formatting (FR-EDT-01), passthrough blocks (FR-EDT-02) and the literal reading of "one live editor at a time" (FR-EDT-03, gate S4-G08) to this task. S4-T01 builds those three things; artefact references, citations and autocomplete stay out of scope for later Stage 4 and Stage 5 tasks.

Before writing code, the installed `@tiptap/markdown@3.31.3` source was read directly (not assumed from memory, AGENTS.md 2.10): `MarkdownManager` has no built-in fallback for bold, italic, inline code, lists, block quotes, code blocks or links — each needs a registered `parseMarkdown`/`renderMarkdown`. Unpacking the installed `@tiptap/extension-bold`, `@tiptap/extension-heading` and `@tiptap/extension-link` 3.31.3 tarballs confirmed the official extension packages already carry these hooks, matching marked's token names — so the schema is composed from `@tiptap/starter-kit`, not hand-written the way S1-T01's spike had to for `artefactRef`/`citation`.

## Decision

1. **Schema.** `packages/format/src/editor/extensions.ts` builds `sectionEditorExtensions()` from `StarterKit.configure(...)`: paragraph, bold, italic, inline code, bulleted and numbered lists, block quotes, code blocks and links stay on; `strike`, `underline`, `horizontalRule` and `hardBreak` are turned off (not in FR-EDT-01). Heading is configured to `levels: [3, 4]` for the live editor's own commands and keyboard shortcuts, but that option does not filter what `Heading`'s `parseMarkdown` accepts (confirmed by reading its source), so it is not what actually keeps other levels out — see the next point.
2. **Passthrough (FR-EDT-02).** `packages/format/src/editor/passthrough.ts` defines the `Passthrough` node (atomic, holds one `markdown` attribute) and `isRepresentable(token)`, which recursively checks a marked token against the schema's supported type names, treating a heading as representable only at `depth` 3 or 4. `markdown.ts` uses `manager.instance.lexer(text)` to get the top-level block tokens *before* calling `MarkdownManager.parse`, so the representability check runs per top-level block: `manager.parse(token.raw)` is only called on a block found fully representable (recursively, including anything nested inside a list or block quote); anything else — a table, raw HTML, a thematic break, a link reference definition, a heading outside levels 3–4, a strikethrough or an image anywhere inside the block — becomes one `Passthrough` node holding `token.raw` verbatim. This never drops or reinterprets content, at the cost of demoting the *whole* enclosing top-level construct (for example, a table inside a block quote demotes the whole block quote) rather than only the unsupported piece; format-v1.md 4.3 reserves level-2 headings for section headings, so those are already split out by `parseExperimentBody` before this parser runs and never reach it. This module lives outside `packages/format/src/schema/`, so it is not a protected-path change.
3. **Single live editor (FR-EDT-03 literal, S4-G08).** `apps/desktop`'s `ExpandedExperimentView` tracks one active section key, defaulting to Methods and resetting to Methods whenever a different experiment is selected (React's documented "adjust state during render" pattern, not an effect). `RichSectionEditor` mounts a real `useEditor`/`EditorContent` instance only for the active section; the other two render `StaticSectionContent`, a small hand-written recursive renderer over the *same* parsed `JSONContent` — not a second Tiptap/ProseMirror instance — activated by click, Enter or Space. Activating a different section naturally blurs the live editor's contentEditable element first, which already flushes its autosave through the existing `onBlur` wiring; no extra flush-before-switch code was needed. `editor-instances.test.tsx` asserts at most one `.ProseMirror` element exists at any point, including after switching.
4. **Save and load path unchanged.** The live editor's `onUpdate` calls `field.onChange(serialiseSectionMarkdown(editor.getJSON()))`, the same `AutosaveField` S2-T12 built; `onBlur` calls `field.onBlur()`. `editExperimentSection`, `setExperimentSection`, `createAutosave` and `useAutosave` are untouched — this task only changes how the text is captured and displayed, not how it is stored or written. No format or schema change.
5. **Passthrough's display.** `packages/format` exports the plain `Passthrough` node (schema and `renderMarkdown`/`renderHTML` only, no React import, AGENTS.md 4). `apps/desktop/src/features/notebook/expanded/liveEditorExtensions.ts` extends it with a NodeView (`PassthroughBlock.tsx`, via `ReactNodeViewRenderer`) that shows the raw Markdown, labelled, and is not editable; `StaticSectionContent.tsx` renders the same block the same way for the two non-live sections.
6. **No toolbar.** Formatting is by keyboard shortcut and Tiptap's own Markdown input rules (`**`, `` ` ``, `-`, `1.`, `>`, ` ``` `, `Mod-Alt-3`/`Mod-Alt-4`) only, per FR-EDT-01's wording (a list of supported syntax, not UI chrome) and to keep this PR's scope to what the row asks; a toolbar or slash menu can be added alongside S4-T02's autocomplete work if wanted.
7. **Dependencies.** `@tiptap/starter-kit@3.31.3` added to `packages/format` (schema only, no React); `@tiptap/react@3.31.3` added to `apps/desktop` (the live editor). Both pinned to the exact version already approved for `@tiptap/core`, `@tiptap/markdown` and `@tiptap/pm` in ADR-0010, from the same release train; `@tiptap/extension-link` was considered but dropped since `@tiptap/starter-kit` already bundles `Link`.

## Not in this task

- Artefact references and their autocomplete (FR-EDT-04 to FR-EDT-06), newer-version updates (FR-EDT-07), detached references (FR-EDT-08) and label/target rewriting on save (FR-EDT-09): S4-T02 to S4-T06.
- Citations (FR-CIT-\*): Stage 5.
- A formatting toolbar or slash menu.
- Full accessibility of the rich editor (screen reader behaviour beyond a labelled, `aria-label`led contentEditable region and an activatable static section): the dedicated accessibility gates (S4-G09, S7-G07) are later tasks.

## Alternatives considered

| Option | Why not chosen |
| --- | --- |
| Hand-write every node's markdown hooks, as the S1-T01 spike did for `artefactRef`/`citation` | Unnecessary: the installed official `@tiptap/starter-kit` extensions already carry these hooks (verified by reading their source), so hand-writing them would duplicate already-correct, already-tested library code. |
| Register a "guard" extension per node type, relying on returning `null` from `parseMarkdown` to fall through to the real handler (mirroring how the official `BulletList`/`OrderedList` extensions share one token name) | The library's own declared `parseMarkdown` return type does not include `null`, so code written this way would not type-check under this repository's strict settings even though the installed library's own source does it internally; splitting by top-level block before parsing avoids the whole question. |
| Disable the other two editors' content entirely while one has focus, to satisfy S4-G08 by the letter, exactly as ADR-0028 rejected for its own textarea version | Same objection ADR-0028 raised: works against showing Results Notes and Interpretation side by side. The chosen design keeps all three visible, one of them live. |
| A single React-managed rich-text renderer with no ProseMirror at all, only for the inactive sections, but rendering the *live* one the same way and diffing on blur | Substantially more code for no benefit over using Tiptap's own `EditorContent` for the one editor that needs to be live; the static renderer only needs to be read-only, which a small recursive function already does well. |

## Consequences

- **Passthrough granularity is the whole enclosing top-level block**, not the smallest possible span. A table inside a block quote demotes the whole block quote to passthrough; this is deliberate (see Decision 2) and covered by `passthrough.test.ts`.
- **A multi-letter alphabetic ordered-list marker at a block's start (for example `"aV. "`) was found, empirically, to make the installed `OrderedList` extension silently drop the letters** when re-parsed (falling back to a plain `"1."`). This is upstream library behaviour, not something `packages/format` works around; the round-trip property test's arbitrary avoids generating that shape (`roundtrip.property.test.ts`, `BLOCK_MARKER_START`) so as not to assert a byte-identical round-trip the library itself does not provide. A real document is very unlikely to contain this shape; if it does, `isRepresentable` still protects against silent loss for constructs outside the schema entirely (tables, raw HTML, etc.), just not against this specific narrower marker ambiguity.
- **jsdom cannot simulate real contentEditable typing.** `RichSectionEditor.test.tsx`'s update-wiring test dispatches an `input` event without a DOM mutation and asserts `onUpdate` reports the *current* document, which proves the `onUpdate → serialiseSectionMarkdown → field.onChange` chain is wired, not that arbitrary typed text flows through end to end (that is `packages/format`'s own, exhaustively property-tested responsibility). This is documented in the test itself.
- **Tests.** `packages/format/src/editor/{markdown,passthrough}.test.ts` and `roundtrip.property.test.ts` (8000+ cases run locally); in the webview, `RichSectionEditor.test.tsx`, `editor-instances.test.tsx` (S4-G08), `StaticSectionContent.test.tsx`, the rewritten `ExpandedExperimentView.test.tsx` and `DetailsPanel.test.tsx`, and the `messages.test.ts` addition for `editLabel`.
- **Windows only.** Everything was run on Windows; the live-editor DOM shape, `EditorProps.attributes` id/`aria-label` wiring and blur-triggered flush have not been seen in a running window on macOS.
