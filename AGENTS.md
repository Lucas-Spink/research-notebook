# AGENTS.md

Rules for AI coding agents (and humans) working on the Computational Research Notebook. Read this file completely before every task. These rules override any conflicting habit or default.

## 1. What this project is

A desktop research notebook built with Tauri 2, React and TypeScript, and Rust. A project is a folder whose `_notebook/` directory holds plain Markdown, YAML and CSL-JSON files. The app is a table-based editor over those files. **The files are the research record; the app must never put them at risk.**

Read before starting any task:

1. `docs/spec/` (the technical specification). The section numbers cited in tasks refer to it.
2. `docs/format/format-v1.md` when touching anything under `packages/format` or any notebook file.
3. `docs/adr/` for decisions already made. Do not reopen a decision without writing a new ADR.
4. `docs/testing-guide.md` before writing tests.
5. The task row in `Development_Stages_and_Test_Gates.xlsx` or the linked issue.

## 2. Non-negotiable rules

Breaking any of these is a failed task regardless of whether CI passes.

1. **Never modify analysis files.** Application code must not write, move, rename or delete anything outside a project's `_notebook/` folder. All Rust filesystem writes go through `nb-fs`. Direct `std::fs` write, rename, copy and remove calls are forbidden elsewhere (enforced by `clippy.toml`).
2. **One parser.** Notebook files are parsed and serialised only by `packages/format`. Never parse Markdown, YAML frontmatter or `artefacts.yaml` anywhere else, including in Rust, the UI or the VS Code extension.
3. **No format changes without approval.** Any change to the on-disk format (spec chapter 5) needs a format version increment, a migration, new fixtures, an ADR and maintainer approval. Stop and ask.
4. **Never weaken tests to pass.** Do not delete, skip (`.skip`, `.only`, `#[ignore]`), loosen assertions, reduce property test case counts, or update golden files to make a failure disappear. If you believe a test is wrong, stop and explain why in the PR for human review.
5. **Never write outside `_notebook/` when parsing fails.** Code paths that fail to parse a file must leave that file untouched and switch to read-only.
6. **No new dependencies without the checklist** in section 7.
7. **No network access** except `127.0.0.1:23119` (Zotero) from `nb-zotero` and the opt-in updater. No telemetry, analytics or remote fonts.
8. **The webview gets no raw filesystem, shell or HTTP access.** Frontend code calls typed commands from `apps/desktop/src/ipc/` only.
9. **Protected paths require human review** (section 6). Make the change if the task requires it, but mark the PR clearly.
10. **Never invent APIs.** Check the installed version's type definitions, docs or `--help` output before using a library function, config key or CLI flag. If unsure, say so.

## 3. Workflow for every task

1. Identify the task ID, the spec sections and the gate tests it affects.
2. If the spec is ambiguous, contradictory or silent on something that affects data, **stop and ask** instead of guessing.
3. Write a short plan in the PR description: files to change, tests to add, risks.
4. Write or extend tests first for any invariant (round-trip, versioning, groups, citations, paths, safety). Confirm they fail for the right reason.
5. Implement the smallest vertical slice that makes them pass: schema, command, UI and tests together.
6. Run `pnpm check` locally, plus the specific suites the task touches (`pnpm test:rust`, `pnpm test:fixtures`, `pnpm test:fs-safety`).
7. Update documentation in the same PR when behaviour visible to users or contributors changes.
8. Fill in the PR template honestly, including what you did not test.

### Stop and ask when

- The change needs an on-disk format or schema change.
- A test cannot pass without changing its intent.
- A new dependency seems necessary.
- The task would delete or overwrite anything a user created.
- You are about to touch a protected path not named in the task.
- Two parts of the spec or ADRs disagree.

## 4. Architecture boundaries

| Component | May depend on | Must not |
| --- | --- | --- |
| `packages/format` | `yaml`, `zod`, `@tiptap/markdown` parsing utilities | Do I/O, import React or Tauri, read clocks or random sources directly |
| `packages/citations` | `citeproc`, `packages/format` types | Do I/O, call Zotero |
| `apps/desktop/src/features/<name>` | `shared/`, `ipc/`, packages, another feature's `index.ts` only | Import another feature's internals, call `invoke` directly, parse notebook text |
| `apps/desktop/src/ipc` | Generated by tauri-specta | Be edited by hand |
| `src-tauri/src/commands` | Crates | Contain business logic |
| `crates/nb-fs` | std, hashing, `notify` | Write outside `_notebook/` |
| `crates/nb-index` | rusqlite | Hold data not reproducible from files |
| `extensions/vscode` | `packages/format`, VS Code API | Write anything except inbox requests |

These rules are enforced by `.dependency-cruiser.cjs`, ESLint restricted imports and `clippy.toml`. Do not disable those checks.

## 5. Code standards

### General

- Use the domain vocabulary from spec chapter 3 exactly: `project`, `question`, `experiment`, `artefact`, `version`, `group`, `membership`, `reference`, `citation`, `citekey`, `source`. Spell `artefact` this way in code and text.
- User-facing text is British English and lives in message files, never inline in components.
- Keep files under roughly 300 lines and functions under roughly 50 lines. Split by responsibility when larger.
- Comments explain why, not what. Public functions and types have doc comments.
- No commented-out code. `TODO` only as `TODO(#issue): reason`.
- Do not reformat unrelated code in a feature PR.
- Generated files (`ipc/`, JSON Schemas) are regenerated by their scripts, never edited.

### TypeScript

- `strict`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` stay on.
- No `any`. No `as` casts except immediately after a Zod parse. No non-null `!` assertions.
- Validate every external input (files, IPC results, Zotero data, clipboard) with Zod at the boundary. Inside the boundary, trust the types.
- Expected failures return a discriminated `Result` (`{ ok: true, value } | { ok: false, error }`). Throw only for programmer errors.
- `switch` over unions ends with `assertNever`.
- Pure functions in `packages/*`: inject clocks (`now: () => Date`) and ID generators (`newId: () => Ulid`) so tests are deterministic.
- Do not mutate function arguments.
- React: function components only. Components render; hooks in the feature own state and effects; logic lives in `model/` modules with unit tests. No IPC calls inside components.
- No `localStorage` or `sessionStorage` for project data. Project data lives in project files.

### Rust

- `#![forbid(unsafe_code)]` in every crate.
- No `unwrap`, `expect` or `panic!` outside tests (workspace lints deny them).
- Library errors use `thiserror` enums; commands map them to typed, serialisable errors.
- Commands accept validated newtypes (`ProjectRelPath`, `ExperimentId`), never raw `String` paths or `PathBuf`.
- Blocking filesystem or hashing work runs in `spawn_blocking` or a dedicated worker, never on the async runtime thread.
- Log with `tracing`, never `println!`.

## 6. Protected paths

Changes here always need maintainer review (also listed in `.github/CODEOWNERS`):

- `apps/desktop/src-tauri/capabilities/` and `tauri.conf.json`
- `apps/desktop/src-tauri/crates/nb-fs/`
- `apps/desktop/src-tauri/crates/nb-archive/`
- `packages/format/src/schema/` and `packages/format/migrations/`
- `fixtures/projects/` (released fixture folders are immutable; add new fixtures instead)
- `docs/format/`, `docs/adr/`
- `.github/workflows/`, `deny.toml`, `clippy.toml`, `.dependency-cruiser.cjs`, `eslint.config.*`, `tsconfig*.json`
- `AGENTS.md`, `CLAUDE.md`

## 7. Dependency checklist

Before adding any dependency, confirm in the PR description:

1. It is needed: no existing dependency or short, tested code does the job.
2. Its licence is on the allow-list (`deny.toml` and `licences:check`) and compatible with AGPL-3.0-or-later.
3. It is maintained: a release within the last 12 months and no unresolved critical advisories.
4. The version is pinned exactly and the lockfile is committed.
5. Its size and transitive dependencies are acceptable for a desktop app.

## 8. Testing rules

- Every behaviour change ships with tests in the same PR.
- Every bug fix starts with a test that fails before the fix.
- Invariant-heavy code (format round-trip, capture and versions, groups, citation contexts, path validation, filename sanitising, atomic writes, verification) requires property tests.
- Tests are deterministic: injected clocks and IDs, fixed or logged seeds, fake timers instead of sleeps.
- Tests use temporary directories only. Never read or write real user folders or the repository's fixtures in place; copy fixtures to a temporary directory first.
- Tests never contact the network except mock servers bound to `127.0.0.1`.
- When a property test finds a failure, add the shrunk case as a permanent regression test.
- Golden files change only through `pnpm golden:update`, with the diff explained in the PR.
- CI fails if tests leave the git working tree dirty.

See `docs/testing-guide.md` for patterns and examples.

## 9. Commands

| Command | Purpose |
| --- | --- |
| `pnpm install` | Install dependencies |
| `pnpm check` | Static checks plus fast TypeScript tests; run before every commit |
| `pnpm test` | All pull-request test suites (TypeScript and Rust) |
| `pnpm test:unit` | TypeScript unit and component tests |
| `pnpm test:property` | Property tests (set `FC_NUM_RUNS` for longer runs) |
| `pnpm test:golden` | Golden file tests |
| `pnpm test:fixtures` | Fixture compatibility |
| `pnpm test:rust` | Rust tests (`PROPTEST_CASES` controls property runs) |
| `pnpm test:fs-safety` | Proves nothing outside `_notebook/` changes |
| `pnpm test:vscode` | VS Code extension tests |
| `pnpm test:e2e` | End-to-end tests (slow; nightly in CI) |
| `pnpm test:a11y` | Accessibility checks |
| `pnpm bench` | Performance benchmarks |
| `pnpm golden:update` | Regenerate golden files (explain the diff) |
| `pnpm lint:rust`, `pnpm format:rust` | Clippy and rustfmt |
| `cargo deny check` | Rust licences and advisories |

## 10. Commits and pull requests

- Conventional Commits with the package as scope: `feat(format): parse artefact references`, `fix(nb-fs): retry rename on Windows sharing violation`.
- One task or concern per PR. Aim for under 400 changed lines excluding generated files and fixtures.
- The PR template checklist must be completed. State which AI tool produced the change and which parts deserve the closest review.

## 11. Definition of done

- [ ] Task definition of done in the workbook is met.
- [ ] Tests written first for invariants; all suites relevant to the change pass locally.
- [ ] CI green on Windows and macOS.
- [ ] No rule in section 2 broken; no lint or boundary check disabled.
- [ ] Documentation and spec updated; ADR added if a decision changed.
- [ ] Protected-path changes flagged for review.
